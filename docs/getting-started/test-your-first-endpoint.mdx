# 🧪 Test Your First Endpoint

<motion.div initial={{ opacity: 0, y: 30 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.6 }}>
Before you deploy anything into production, it's crucial to simulate how your API will respond in both expected and unexpected situations. The foundation of that process starts with testing <HoverExplain word="endpoints" definition="Specific URL paths within your API that accept requests like GET, POST, PUT, DELETE, etc." />, which act as the building blocks of all interactions between client and server.

Endpoints represent not just routes, but contracts—defining exactly what input they accept, what output they provide, and what types of responses (success or failure) they produce. In this section, you’ll learn how to **test live endpoints** using Swagger and Redoc; simulate edge cases and invalid requests; and confirm whether your <HoverExplain word="OpenAPI spec" definition="A standardized, machine-readable description of your API, including endpoints, methods, and schemas." /> matches the actual behavior of your mock or live server.
</motion.div>

## 🛰️ What Is an API Endpoint Really?

<SpotlightCode
  title="GET Request Example"
  yamlCode={`get:
  summary: Get all users
  responses:
    '200':
      description: A list of users`}
  jsonCode={`{
  "method": "GET",
  "endpoint": "/users",
  "response": {
    "status": 200,
    "data": ["user1", "user2"]
  }
}`}
  highlightLines={[1, 3]}
/>

<motion.div initial={{ opacity: 0, y: 30 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.6 }}>
An endpoint, conceptually, is a **touchpoint between your consumer and your server logic**. In a RESTful API, endpoints are mapped to logical resources such as `/users`, `/posts`, or `/payments`; each resource is then manipulated through verbs like `GET`, `POST`, `PATCH`, or `DELETE`.

For example, `GET /users` retrieves a list of users; `POST /users` adds a new user; `DELETE /users/:id` removes a specific user.

What matters most is that these are not just arbitrary URLs; they are documented, versioned, and expected to behave predictably. Their responses, error codes, and accepted parameters are defined in your YAML and enforced by validators or mock servers. This makes API endpoints both **contractual** and **testable**.
</motion.div>

## 🧯 Simulate Errors, Invalid Requests, and Edge Conditions

<motion.div initial={{ opacity: 0, y: 20 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.5 }}>
To build a **reliable API**, it’s essential to simulate how things behave when they go wrong. Using Swagger, Postman, or curl, try submitting incomplete JSON payloads, unauthorized tokens, or malformed requests. Doing this allows you to confirm that your API returns appropriate status codes, such as: `400` for malformed input; `401` for missing auth headers; `500` for internal logic failures.

<SpotlightCode
  title="Error Response Example"
  yamlCode={`responses:
  '400':
    description: Missing required field
  '500':
    description: Internal server error`}
  jsonCode={`{
  "400": "Missing required field",
  "500": "Internal server error"
}`}
  highlightLines={[2, 4]}
/>

When your YAML accurately reflects these conditions, your frontend and partner teams can **design their error handling** and retries with confidence.
</motion.div>
