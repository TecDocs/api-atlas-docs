## 🗂️ GitOps Directory Structure

<GitOpsDirectoryViewer />

<motion.div initial={{ opacity: 0, y: 30 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.6 }}>

<p>
A well-structured GitOps repo is like a city blueprint. Zones are clearly marked, utilities are shared but separated, and every layer can evolve independently. The directory viewer above reveals this model in practice: <code>/base</code> for universal Helm templates, <code>/envs</code> for per-environment logic, and <code>/secrets</code> for isolated credentials.
</p>

<p>
When a pipeline runs, it knows exactly where to look. Dev may override resource limits, staging might inject a new image tag, production ensures strict probes and RBAC. This follows the same logic you explored earlier when templating with <HoverExplain word="Helm" definition="The package manager for Kubernetes that supports reusable, versioned templates." /> and injecting secrets via your pipeline.
</p>

<p>
This structure isn’t just clean, it’s enforceable. CI/CD systems can lint the layout, block missing values, and prevent drift. Before you scale clusters, you need scalable definitions. Now let’s widen our lens to handle multi-cluster delivery.
</p>

</motion.div>

## 🌐 Multi-Cluster Delivery Strategy

<MultiClusterDiagram />

<motion.div initial={{ opacity: 0, y: 30 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.6 }}>

<p>
The diagram above maps how your GitOps system fans out into multiple clusters. Imagine your environments as branches on a tree. Git defines the trunk, and tools like <HoverExplain word="Flux" definition="A GitOps agent that continuously syncs Git state to Kubernetes." /> or <HoverExplain word="ArgoCD" definition="A declarative GitOps tool for Kubernetes." /> ensure each branch grows in harmony.
</p>

<p>
Each cluster watches only its scope, prod-west, staging, or dev. Pipelines update Git, and Git defines cluster state. This separation reduces blast radius and supports fast rollbacks. It also aligns perfectly with what you learned in <code>ci-cd-setup</code>; pipelines modify Git, not the cluster directly. The cluster pulls trusted state.
</p>

<p>
You’ve now scaled infrastructure horizontally. But change also moves vertically, through Git branches. Next, we’ll explore how promotion strategies enable confidence and control.
</p>

</motion.div>

## 🌳 Branching & Promotion Strategy

<BranchStrategyFlow />

<motion.div initial={{ opacity: 0, y: 30 }} whileInView={{ opacity: 1, y: 0 }} transition={{ duration: 0.6 }}>

<p>
This promotion strategy shows how changes flow across branches. <code>feature/* </code> branches go to <code>dev</code> clusters, <code>release/*</code> moves to staging, and <code>main</code>? That’s your production trigger. This aligns directly with your CI/CD configuration and Helm overrides from <code>pipeline-stage-viewer</code> and <code>helm-deploy-configurator</code> earlier.
</p>

<p>
Each branch acts as a quality gate. Features undergo linting and sandboxing, staging validates secrets and autoscaling, and production enforces policies. Git becomes more than version control, it becomes a policy engine. That’s what modern delivery needs.
</p>
